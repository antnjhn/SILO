# Uninstaller backend contract

- `discover_uninstallers(game_id)` returns one-time opaque candidate IDs for executable-looking uninstaller files directly in the canonical game root. A new scan replaces only that game's prior tokens; tokens for other games remain until TTL expiry or global capacity eviction. The cache is bounded to 512 entries and tokens expire after five minutes.
- `run_uninstaller_candidate(game_id, candidate_id)` consumes the token before validation, checks game ownership and unchanged canonical root, then revalidates containment, regular-file status, supported executable extension, size, modification time, and file identity. Unix identity is `(device, inode)`; Windows identity uses volume serial and file index when the OS supplies them. Windows reparse-point candidates are rejected.
- Immediately before spawning, the backend opens the path and compares metadata/identity from that same open handle to the scanned identity. On Windows it also rejects `FILE_ATTRIBUTE_REPARSE_POINT` on the held handle and opens with sharing that denies write and delete/rename replacement while the handle remains alive through process creation. **Residual limitation:** `std::process::Command` still launches by pathname, not by the verified handle; this is not a fully handle-based launch and remains dependent on Windows pathname resolution semantics. Use only in trusted game directories.
- No arguments are supplied to the child process. Discovery output includes filename and relative path for display; callers must pass the opaque candidate ID, not construct executable paths.

## Permanent game-folder deletion policy

`delete_game_folder(game_id)` retains its existing IPC signature, but derives the target only from the matching library record's configured `exePath`; it does not accept a caller-supplied filesystem path. Deletion is allowed only when the executable path is absolute, resolves to an existing regular file, and its canonical parent can be established. The target leaf itself must identify the game; a matching ancestor does not establish ownership (so an ordinary `Games/Example Game` layout is accepted only because `Example Game` is the leaf). Generic/shared leaf names such as `Games`, `SteamApps`, `Common`, `Applications`, `Apps`, `Program Files`, and `Library` are refused independently of game-name matching. Filesystem roots and targets equal to or beneath OS/system and program-install roots are refused. The home/profile directory itself and its `Desktop`, `Documents`, `Downloads`, `Videos`, `Pictures`, and `Music` directories (including descendants) are refused; other ordinary home descendants such as `HOME/Games/Example Game` are not rejected merely because they are beneath the home directory. A target containing another registered game's configured executable is refused based on its absolute lexical path and, where possible, the resolved path or canonical parent. If that other path is ambiguous or cannot be resolved sufficiently to establish it is outside the target, deletion fails closed with guidance to correct/remove that library path. Any symlink or Windows reparse-point component in the configured path or resolved target is refused. The target is canonicalized and safety-checked again immediately before `remove_dir_all`.

“Valid game-folder delete” therefore means deleting only that verified dedicated game directory, not the common library containing it. If the executable or install root is missing, non-absolute, linked, or otherwise ambiguous, the backend fails closed with an actionable error; UI confirmation does not override these checks. This remains pathname-based protection: the final re-resolution and checks narrow but do not eliminate races between validation and `remove_dir_all`; deletion is not handle-relative, and filesystem changes in that interval may still redirect or alter the affected tree. The uninstaller execution flow is unchanged.
